## 1. 需求背景

在互联网可达的环境下， 我方有N个系统，这N个系统有对外用户使用的比如用户个人中心，开发者控制台系统；有内部管理类型的系统比如用户管理系统，权限管理系统；有公司内部的审批系统；有数据处理的系统；有网关类系统；有统一认证中心系统；这N个系统中类型多元化存在，每个系统的功能辐射也不一样，每个系统所使用的“用户群体”也都不一样对应的数据库表也不一样。

基于上述的叙述的当前环境系统分布情况，现在需要开发一个主框架系统，主框架定义如下：
这个“主框架系统”负责统一管理所有系统的注册，分发，授权（可访问权限与用户粒度），用户管理，日志溯源，文件存储，短信配置，邮件配置，服务监控，通知配置等。

## 2. 核心需求

“主框架系统”核心就是统一管理用户 与 统一管理配置

## 3. 当前问题

1. 在若干个子系统下有一部分是集成了CAS统一认证中心的，例如：用户系统，权限系统，地图服务系统，数据服务系统等。
2. 在若干个子系统下有一部分虽然集成了CAS统一认证中心，但是某些门户地址，首页地址是不需要登录就可以访问的，当前是依靠CAS配置项进行管理配置的。
3. 在若干个子系统下有一部分虽然集成了CAS统一认证中心，但是当前分为普通用户（客户端用户）和管理员（管理系统类）用户；比如用户系统分为个人中心系统，用户管理后台系统，这两个系统中即使同一个用户，在个人中心系统登录不一定可以登录用户管理后台系统，必须这个人被赋予管理员角色才可以登录。
4. 在若干个子系统下有一部分系统下的用户是这个系统内特有的用户，角色也是系统特有的角色，比如在用户管理后台系统角色名称为国家管理员，但是在数据服务系统中是审计管理员，人员所在数据库表不一样，角色定义也不一样；
5. 在若干个子系统下有一部分系统不集成CAS统一认证中心，登录授权技术或框架是特立独行的存在，完全自成一派。当然这类的系统属于少量，微乎其微，但是不能否认这类系统的不存在。
6. 在即将开发的这个“主框架系统”模式下，是否每个子系统还有必要保留CAS-client集成模式，如果移除每个子系统与CAS统一认证中心的模式，将CAS统一认证中心改为与“主框架系统”集成，这样每个子系统就需要单独去维护用户session，缓存，监听，拦截；这样代价是有点大的；如何在保留子系统与CAS统一认证中心集成的这种模式下与“主框架系统”高度自适配
7. “主框架系统”扮演的角色和CAS统一认证中心不能冲突？如何处理这种关系映射。是否每个子系统提供接入“主框架系统”的适配接口进行“主框架系统”的“服务注册”与“用户数据同步”，可访问可控制权限交予“主框架系统”之中。
8. 对于不需要登录就访问的地址连接也需要进行控制，对于需要登录的访问地址连接在触发用户登录之后如何平衡“主框架系统”和CAS统一认证中心授权的奇点。既然对于用户进行了统一的管理，那么“主框架系统”应该能绝对控制所有子系统中的所有用户在访问子系统的前置权限；所谓的前置权限指的是：子系统内部的权限控制还是由子系统内部进行逻辑控制，但是在实际到达子系统内部的逻辑控制前，是交予“主框架系统”进行控制的。
9. “主框架系统”关于权限分配的问题，需要兼容是否必须用户登录，是否是管理员还是普通用户，默认配置，全局配置等因素

## 4.  需求功能清单

 功能1：用户管理：对于子系统所有用户进行统一管理，统一授权，统一配置，统一数据同步；
     - 数据同步：在主框架系统中，每次接入一个子系统都需要将子系统中的所有用户进行同步到主框架之中，子系统提供数据同步的对接接口，主框架负责“pull"子系统的所有用户数据；同时也提供每晚0点定时同步所有接入主框架的子系统的所有用户信息。
     - 统一管理：所有子系统的用户将在主框架中进行条件筛选，展示功能管理，不提供删除用户功能。列表提供展示可访问系统列与按钮控制
     - 统一授权：提供单用户授权，和批量用户授权两种方式，授权粒度如下：
         - 黑白名单：
         - 访问系统：（注意：在功能2中的未开放的系统在这里将不予罗列展示）
         - 地区归属：
         - 自定义配置：
         - 角色控制
 功能2：系统注册：在主框架配置页面配置子系统注册到主框架的相关配置
    - 系统名称：子系统名称
    - 系统编码：子系统唯一编码
    - 系统访问地址：子系统访问URL
    - 系统配置地址：子系统nacos配置项-后续可拓展移植
    - 系统接入地址：子系统接入的接口
    - 系统接入配置：子系统使用的CAS配置项，如果无则为空
    - 会话路径：子系统cookie.path
    - 系统元数据属性：子系统特殊的配置json项
    - 系统注册列表：已经注册在主框架的所有子系统
 功能3：子系统访问权限控制：在主框架配置页面进行配置子系统访问权限
    - 配置单元要素1：是否可访问：按照全局，黑白名单，地区归属，角色，登录者，自定义配置六种level进行配置，在允许访问范围内可访问系统；在不允许访问权限下禁止访问；
    - 配置单元要素1示例：
        - "全局配置可访问&非黑名单&河北地区&省级管理员" |--> 天津用户将无法访问
        - "全局配置可访问&非黑名单&河北地区&省级管理员&张三" |--> 河北李四无法访问
        - "全局配置可访问&非黑名单&河北地区&省级管理员&test&必须返回mark" |--> 河北zhang用户返回信息没有mark无法访问
    - 配置单元要素2：每个注册上来的子系统都有默认的权限，初始化子系统默认都可以访问；
    - 配置单元要素3：是否开放子系统：是否开放子系统和是否可访问并不冲突，注册到主框架系统上的所有子系统在没有准备好之前默认都是“否”状态。
    - 可访问权限优先级顺序：开放状态>自定义配置>登录者>角色>地区归属>黑白名单>全局配置>默认配置
 功能4：通知配置：在主框架配置页面进行配置子系统的通知栏位所使用的配置
     - 配置范围：可全局配置，可按系统配置，附带一个默认配置
     - 默认配置：当子系统不进行单独配置的时候，会读取全局配置
     - 子系统配置通知：负责配置子系统的通知配置，子系统的通知功能直接读取主框架给子系统配置的通知配置项，不要再在子系统繁琐的配置；
 功能5：短信/邮件配置：在主框架配置页面进行配置子系统的发送短信/邮件，发送功能由主框架提供，每个子系统按需按具体功能调用主框架发送短信/邮件的api接口。
    - 配置范围：与功能4保持类同
    - 默认配置：与功能4保持一致
    - 子系统配置：负责配置单独子系统短信，邮件所使用的信息
 功能6：文件存储：每个子系统文件存储的位置，如没有使用可不配置，每个子系统需要读取主框架的配置
    - 配置范围：与功能4保持类同
    - 默认配置：与功能4保持一致
    - 子系统配置：负责配置单独子系统文件存储，邮件所使用的信息
 功能7：dashboard 控制台首页
    - 子系统罗列：罗列接入的子系统；点击卡片可直接进入对应的子系统之中。
    - 统计信息：展示用户数量，接入子系统数量，角色引用，安全警告
    - 服务监控：监控每个系统的运行情况，启动次数，硬件信息
    - 日志溯源：站在主框架的角度记录每个登录者的访问系统及在主框架配置修改
 功能8：日志管理：日志管理是指的主框架的操作日志与子系统经过主框架授权链路的访问日志，与日志溯源的不同的是：日志溯源只罗列当前5条授权概览和最近操作（即在主框架的操作日志）
     - 操作日志：在主框架上的配置，授权，管理等主框架本身系统的操作日志
     - 访问日志：子系统在访问的时候，触发主框架的拦截链路的访问日志
