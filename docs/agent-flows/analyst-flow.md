# Analyst Flow 需求分析运行规格

本文件是 `agents/analyst.md` 的内部推演规格，不是访谈脚本，不是 Claude Code agent 文件，不包含 agent frontmatter，不被主调度器直接调用。

## 1. 定位与边界

`analyst` 是 Superlooper AI 并行流程编排中的需求分析 subagent。它的价值不是把自然语言需求逐项转问用户，而是在进入设计、开发、测试和 review 前，先完成自动化深度透析。

本文件只约束 `analyst` 的内部分析流程，不覆盖 `agents/analyst.md` 的 payload、PRD 输出路径、PRD 输出格式和禁止事项。当本文件与 `skills/superlooper/SKILL.md` 冲突时，以主调度协议为准。

职责边界：`agents/analyst.md` 是输出契约源，负责状态块、PRD 模板、质量扫描和禁止事项；本文件是内部推演源，负责分析顺序、分类判断和交互力度控制。两者重复时，正式输出以 `agents/analyst.md` 为准。

## 2. AI 编排运行原则

### 2.1 默认推断原则

对于缺失信息，`analyst` 不得优先反问。必须先基于原始需求、当前上下文、通用工程约束和行业最佳实践进行合理推断，并显式标记为 `[假设]`。

| 信息状态 | 处理方式 | 默认证据强度 |
| --- | --- | --- |
| 原始需求明确说明 | 记录为 `FACT-*` | `EVIDENCE_HIGH` |
| 可基于上下文高置信推断 | 记录为 `INFER-*` 或 `ASM-*`，并标记 `[假设]` | `EVIDENCE_MEDIUM` |
| 不影响需求方向、合规边界或核心业务指标 | 记录为 `OPEN-*` 非阻塞开放问题，允许 PRD 进入设计 | `EVIDENCE_LOW` / `EVIDENCE_MEDIUM` |
| 属于后续设计决策 | 标记为后续 `architect` 处理，不在需求阶段追问 |
| 已由用户确认或可采用默认建议的关键路径 | 记录为 `DEC-*`，状态为 `CONFIRMED_BY_USER` 或 `DEFAULT_ACCEPTED`，允许进入正式 PRD |
| 存在互斥且影响需求方向、合规边界或核心业务指标 | 升级为外部阻塞 `DEC-*`，输出关键决策看板，不生成正式 PRD |

### 2.2 批处理确认原则

`analyst` 在内部推演过程中禁止碎片化反问。所有需要用户确认的内容必须合并到最终输出的“关键决策看板”中一次性呈现。

### 2.3 深度透视原则

`analyst` 不只记录用户说过的话，还必须挖掘用户没说但需求成立必须满足的前提条件，包括状态一致性、资源竞争、跨边界协作、敏感操作、失败补偿、可观测性和合规边界。

### 2.4 只升关键岔路口原则

只有当推断存在两个以上逻辑自洽但互斥的路径，且无法通过上下文概率判断默认方向时，才允许升级为 `DEC-*` 并交给用户决策。

## 3. 内部透析五层

以下五层是内部推演顺序，不是五轮用户交互。

### 3.1 语义解构与实体归一化

将原始自然语言拆解为结构化元素：

| 元素 | 编号 | 说明 |
| --- | --- | --- |
| 角色/主体 | `ACTOR-*` | 使用者、管理者、审核者、外部参与者或系统参与方 |
| 领域对象 | `ENTITY-*` | 需求中被操作、被管理、被流转或被约束的业务对象 |
| 行为 | `ACTION-*` | 创建、查询、变更、提交、审核、撤销、同步、通知等业务行为 |
| 状态 | `STATE-*` | 领域对象的生命周期状态、流转状态或处理状态 |
| 结果 | `OUTCOME-*` | 行为完成后必须产生的业务结果、数据结果或可观察结果 |

若用户未提供命名，`analyst` 自行生成语义化名称并标记 `[假设]`，不得因命名缺失向用户提问。

P0 需求至少需要一个 `EVIDENCE_HIGH` 来源；只有 `EVIDENCE_MEDIUM` 或 `EVIDENCE_LOW` 支撑时，必须补充依据、降低优先级，或转入 `OPEN-*` / `DEC-*`。单个 P0 需求关联的 `ASM-*` 数量不得超过事实、决策和高置信推断来源数量；同类工程默认假设必须合并为全局 `ASM-*` 后通过编号引用。

### 3.2 隐性前置条件推演

从需求成立所需的底层前提中补齐隐性要求。

| 前提类型 | 自动沉淀方向 | 进入 PRD 的位置 |
| --- | --- | --- |
| 状态一致性 | 幂等、防重复、状态流转约束、冲突保护 | `REQ-*` / `NFR-*` / `AC-*` |
| 资源竞争 | 并发控制、边界保护、冲突处理 | `NFR-*` / `CON-*` / `AC-*` |
| 跨边界协作 | 超时、重试、补偿、最终一致性、失败可恢复 | `NFR-*` / `CON-*` / `AC-*` |
| 敏感操作 | 权限、审计、留痕、可追责、最小授权 | `CON-*` / `NFR-*` / `AC-*` |
| 失败路径 | 异常处理、回滚、补偿、告警、人工介入入口 | `REQ-*` / `AC-*` / `OPEN-*` |

这些内容默认由 `analyst` 内部推演沉淀，不作为普通澄清问题抛给用户。

### 3.3 歧义消解与度量显式化

将口语化、形容词化或不稳定表达转换为可验证的初始需求假设。

| 模糊类型 | 转换方向 |
| --- | --- |
| 时间类模糊 | 响应时间、处理时限、等待上限、超时边界 |
| 容量类模糊 | 数量级、大小、吞吐、并发、批量上限 |
| 安全类模糊 | 权限边界、数据保护、审计要求、敏感信息处理 |
| 稳定性模糊 | 失败处理、恢复能力、补偿机制、告警能力 |
| 易用性模糊 | 操作步骤、反馈可见性、错误提示、容错能力 |

若用户未明确量化，采用合理默认阈值并标记 `[假设]`。若该阈值直接决定业务成败且无法估算，升级为 `DEC-*`。

### 3.4 对抗性完备性检测

`analyst` 必须主动模拟异常、滥用、边界和极端运行场景，对现有需求进行压力检查。

| 检测维度 | 必须检查 |
| --- | --- |
| 批量行为 | 上限、进度可见性、部分失败、取消、重试 |
| 外部依赖 | 超时、降级、重试、补偿、依赖不可用 |
| 数据异常 | 校验、拒绝、回滚、告警、自恢复 |
| 权限边界 | 越权、误操作、审计缺口、职责分离 |
| 生命周期 | 创建、变更、暂停、终止、恢复、归档 |

检测产物不得停留在评论中，必须进入 `REQ-*`、`NFR-*`、`CON-*`、`AC-*`、`OPEN-*` 或 `DEC-*`。

### 3.5 多角色视角补全

`analyst` 必须从多个角色视角补全需求，不得只按直接使用者视角分析。

| 视角 | 补全方向 |
| --- | --- |
| 使用者视角 | 可用性、容错性、反馈可见性、操作可理解性 |
| 管理者视角 | 审核、统计、追踪、策略控制、留痕 |
| 交付者视角 | 可观测、可回滚、可维护、可验证、可诊断 |
| 合规者视角 | 数据边界、授权、留存、删除、审计、责任归属 |

## 4. 人机交互力度控制

### 4.1 禁止碎片化反问

`analyst` 禁止在流程中途发起多轮零散问题。分析过程中发现的缺口必须先进入内部假设池、开放问题池或决策池，最终统一输出。`OPEN-*` 不得触发流程二停止；只有外部阻塞 `DEC-*` 可以触发 `ANALYST_BLOCKED_BY_DECISION`。

### 4.2 关键决策升级索引

关键决策、风险等级、证据强度、`DEC-*` 状态枚举、用户确认后的二次生成规则和需求变更规则，以 `agents/analyst.md` 为准；本文件不重复维护完整契约。

内部推演只保留分流索引：

- 触及合规、安全、权限、数据正确性或 `MUST_NOT` 时，先执行 `agents/analyst.md` 的冲突优先级，不得被默认推断、`OPEN-*` 或压缩去重弱化。
- 能按上下文补齐的信息进入 `ASM-*`；不改变需求方向的执行细节进入 `OPEN-*`；已确认、默认采纳、延期非阻塞或被替代的关键选择进入正式 PRD 的决策记录。
- 无法默认且会影响 PRD 正确性、合规边界或核心业务目标的互斥选择，进入外部阻塞 `DEC-*`，并触发 `ANALYST_BLOCKED_BY_DECISION`。
- 用户确认关键决策、提交自然语言 PRD 反馈并由主调度器归一化为 `PRD未通过，按反馈重新分析` 后，必须保持编号稳定、标明替代关系，并按 `agents/analyst.md` 的差异化分析规则重新生成基线。

### 4.3 强管控禁止项

- 不询问可通过工程常识默认成立的问题。
- 不询问可由 `analyst` 自行命名、归类、编号的问题。
- 不询问属于后续 `architect` 的技术设计问题。
- 不询问不影响 PRD 正确性的展示细节。
- 不把字段命名、页面形态、内部模块划分作为需求阶段阻塞问题。

### 4.4 关键决策看板路由

所有外部阻塞 `DEC-*` 必须合并输出为一个关键决策看板；已确认、默认采纳、延期非阻塞或被替代的 `DEC-*` 进入正式 PRD 的决策记录。看板字段、数量限制、示例防污染和状态块要求，以 `agents/analyst.md` 为准。

## 5. 输出状态规则

输出状态、状态块字段、完成定义和质量扫描失败处理，以 `agents/analyst.md` 为准。本文件只约束内部路由：

- 存在外部阻塞 `DEC-*` 时，只输出关键决策看板，不写正式 PRD。
- 不存在外部阻塞 `DEC-*` 且满足需求阶段完成定义时，写入正式 PRD 并输出 `READY_FOR_DESIGN`。
- 写入正式 PRD 后，必须输出 `.superlooper/reports/<session_id>/upstream_alignment.md`，对照原始需求完成 PRD 保真自校对。
- 任一质量扫描组不通过时，不得把流程二标记为可进入设计；必须按问题性质回流到 `ASM-*`、`OPEN-*`、降级处理或关键决策看板。

## 6. PRD 映射规则

分析产物必须映射到 `agents/analyst.md` 的 PRD 输出结构。Mermaid、Given-When-Then、YAML 状态块、人工审核焦点摘要、模板防污染、P0 最小闭环、字段最小表达、输出密度和 PRD 去重规则，以 `agents/analyst.md` 为准；本文件只保留产物到章节的路由关系。

| 分析产物 | PRD 位置 |
| --- | --- |
| `FACT-*` | 原始需求汇总 |
| `INFER-*` | 事实、推断与非阻塞开放问题 |
| `ASM-*` | 假设声明 |
| `DEC-*` 外部阻塞 | 独立关键决策看板，状态为 `ANALYST_BLOCKED_BY_DECISION` |
| `DEC-*` 已确认、默认采纳、延期非阻塞或被替代 | 正式 PRD 的决策记录章节，且必须包含决策状态、默认建议和影响范围 |
| 输出状态块 | 关键决策看板或正式 PRD 的机器可读状态块 |
| `ACTOR-*` | 干系人与适用对象 |
| `ENTITY-*` / `ACTION-*` / `STATE-*` / `OUTCOME-*` | 需求定义、问题归宗、验收标准 |
| `PROB-*` | 问题归宗 |
| `OBJ-*` / `SUCCESS-*` | 业务目标与成功标准 |
| `REQ-*` | 需求定义总览、功能性需求定义 |
| `NFR-*` | 非功能性需求定义 |
| `CON-*` | 约束与合规要求 |
| `AC-*` | 验收标准 |
| `OPEN-*` | 正式 PRD 的非阻塞开放问题章节和追溯矩阵；必须包含建议处理阶段和默认处理方式 |

## 7. 后续消费映射规则

后续 agent 对 `DEC-*`、`OPEN-*`、`AC-*` 和追溯矩阵的消费契约，以 `agents/analyst.md` 与 `skills/superlooper/SKILL.md` 为准。本文件只要求内部推演在生成 PRD 前确认：

- `DEC-*` 与 `OPEN-*` 有明确影响范围、建议处理阶段和默认处理方式。
- `OPEN-*` 的默认处理方式可转换为设计约束、实现约束、测试依据或审查检查项。
- 无法被后续 agent 消费的问题必须重新归类为 `ASM-*` 或 `DEC-*`。

## 8. 原始需求保真规则

原始需求是事实源，PRD 是需求执行基线。`analyst` 必须通过编号与追溯矩阵保证结构化后的 PRD 没有丢失原始需求语义。

- 原始需求中的明确事实必须进入 `FACT-*`。
- AI 推断必须进入 `INFER-*` 或 `ASM-*`，不得伪装成用户明确要求。
- 关键互斥路径必须进入 `DEC-*`，不得暗中选择。
- 每条 P0 需求必须能回溯到 `FACT-*`、`INFER-*`、`ASM-*` 或 `DEC-*`。
- 后续 agent 以 PRD 为执行入口，但必须能通过追溯矩阵回看事实来源。

## 9. 禁止事项

- 不输出访谈式阶段报告。
- 不把内部分析层级当作用户交互步骤。
- 不因模板中存在问题就向用户发问。
- 不把普通模糊点升级为阻塞项。
- 不把技术选型、架构设计、模块拆分、接口设计、数据库设计、类名、函数名或代码实现写入需求分析结果。
- 不在正式 PRD 中残留 `...`、`TBD`、`TODO`、`待确认`、`待补充`、`后续处理` 等占位或未归类内容；所有不确定内容必须归入 `ASM-*`、`OPEN-*` 或 `DEC-*`。
